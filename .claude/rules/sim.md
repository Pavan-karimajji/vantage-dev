| ID | Rule |
|---|---|
| R-SIM-1 | **Framework at the root, content in the component.** The simulation/visualization framework lives once in `modules/sim` (`adas-sim`); a component contributes only plug-ins under `modules/<name>/sim/` (layer providers, port manifest, pipelines, viewpoints, sensor models). **The framework's own source must never contain the strings `aeb`/`bsd`/`lca`/`acc`/`ldw`/`lka`** — a grep is the enforcement, same test `R-ARCH-2` uses for middleware-free algorithm code. **Scope, stated because it was ambiguous until 2026-08-04:** the enforced surface is `modules/sim/src/**` (`GT-1`, mechanised in `scripts/check_invariants.py`), **not** `modules/sim/tests/**`. A parity or golden test must be able to name the component it achieves parity with — `tests/fixtures/make_bsd_golden.py` replays a real component's layers to build the golden `ST-B1-1` compares against — so a test naming a function is evidence the framework works, not a leak into it. The line that matters is *shipped framework code has no function in it*; widening the grep to `tests/` would delete real coverage to protect a slogan. **Placement, in order:** cross-cutting knowledge / backlog / orchestration → superproject root (which holds **no source code**); names one function or component → that submodule; a **component-agnostic GUI toolkit naming no function and no component** → its own submodule (`modules/viz`, a case this rule did not anticipate because the toolkit did not exist when it was written — kept out of `modules/sim` itself by `viz_concept.md` §7's `viz → sim` dependency-cycle reason, `VZ-22`); otherwise → `modules/sim`; build machinery is the exception (byte-identical copies, `R-BUILD`). **This rule fixes where a plug-in is *authored*, not how it is *delivered*** — see `R-SIM-20`, without which "the framework is standalone" and "the picture lives in the component" read as a contradiction. |
| R-SIM-2 | **Layer providers emit geometry; renderers emit pixels.** A provider returns `Layer`s of `Prim`s in **metres, in a named frame** (`ego` by default, `R-COORD-1`), styled by **semantic token** (`"zone.entry"`), never by colour. A provider never computes a pixel, reads the viewport, imports a renderer or a GUI toolkit, touches disk or holds state between ticks — **the provider is `viz`'s C++ `SceneBuilder`/plug-in today** (`SM-10`, 2026-08-26); a Python provider is prototyping-only and never ships (`D-4`), so this rule binds whichever language is authoring the plug-in, not one specifically. One `width_px`/`offset_px` exception exists for line weight and label offset — legibility is not physical. **A `Prim` inlines small geometry only** (`NR-SIM-43`, `OD-7`): bulk arrays — point clouds, images, occupancy grids — are **referenced** by topic + `log_time_ns` into the recording and resolved by the renderer at draw time, under a declared per-Scene budget — `SceneBuilder::CheckInlineBudget` in `viz`'s C++ (`scene_builder.cpp`, `kMaxInlinePrimElements`, refuses with `VizError::kBudgetExceeded` naming the layer and the count), `Layer.__post_init__` in the retired Python. The bounded-history cache (`viz`'s `SceneHistory`/`SceneCache`, `max_bytes`, `scene_history.hpp`) bounds by **bytes**, not entry count, in both languages. This is enforceable precisely because `R-SIM-7` holds: if a value is big it came from a port, and if it came from a port it is in the recording. |
| R-SIM-3 | **Configuration is the source of geometry.** Ego body, object footprints, sensor poses and camera intrinsics come from the project's YAML resolved per run — never a module constant. Switching project must change the picture. A footprint that is a fallback rather than a measurement is drawn with the `assumed_geometry` style so it is visibly a guess. |
| R-SIM-3a | **One atomic config bundle per (project, build), packed beside the library.** The build copies `src/project/<p>/default.yaml` + `shared_config`'s `vehicle/ego_params.yaml` + the port manifest into `<library_dir>/config/` with a `bundle.sha256`; `adasInit(NULL)` resolves it module-relative, an explicit path always wins, and a project mismatch is a **warning**. Authoring homes are unchanged (`R-VAR-4`) — the bundle is a build **output**, never a second place to edit a value. Copied **beside** the DLL, never compiled into it (that would kill the edit-and-re-run calibration loop; production uses AUTOSAR frozen parameters instead, `R-SIL-1`). **The viewer must read the bundle the SUT was initialised with**, resolving embedded-in-recording → library `config/` → source checkout, and **stating which** — the two readers agreeing by coincidence is the failure this exists to prevent. **One bundle per component, permanently** (`OQ-1`, `OD-11`) — a bundle is a build output and a pipeline is a run-time composition, so a per-pipeline bundle would be either unbuilt or hand-assembled, i.e. the second edit site this rule forbids. The multi-component risk is answered by two load-time checks, not by a second artifact: **project agreement** across manifests (a warning, with a declared `allow_mixed_projects:` escape that is badged and recorded) and **ego-parameter agreement** across the bundles' copies of `shared_config`'s `vehicle/ego_params.yaml` (a **hard error, no escape** — two components disagreeing about the wheelbase is a wrong result *and* a wrong picture, with no legitimate reading). |
| R-SIM-4 | **Ports are named and discovered, never positional.** One generic ABI (`adasInit`/`adasExec`/`adasShutdown`/`adasManifest`/`adasAbiVersion`) plus a per-component port manifest generated from `ENABLED_FUNCTIONS`. **Adding a function adds a manifest line, never an ABI parameter and never a host edit.** Port names are `<function>.<port>` using the same token as `src/component/<fn>/` and `ENABLED_FUNCTIONS`. The producer half is generated, not hand-written (`R-SIM-22`); the consumer half binds by lookup, not by literal (`R-SIM-21`). |
| R-SIM-5 | **sim / resim / replay are three different things.** *sim* = a run that **produces** a recording while executing (`SW-0233`'s middle verb; there is no live world model, `DD-12`). *resim* = SUT re-executed against a recording, **deterministic and the only thing that goes in CI**. *replay* = a recorded result rendered with no computation. Never call a resim a replay. |
| R-SIM-6 | **Every declared port — every stage's inputs *and* outputs — is recorded, and every run carries a manifest.** The recorder derives its topic list from the pipeline's port manifests, so "did we record everything the SUT reads?" is true by construction. **Outputs are not optional:** a stimulus-only recording can be resimmed exactly one way, whereas a recording containing every stage's outputs supports any cut point (R-SIM-10) and a free simulated-vs-recorded comparison — for a few kB per tick of data already computed. A sim run writes a session recording by default. A recording states its scenario, project, pipeline, component build hashes, config-bundle hash and ABI/manifest versions, and **embeds the config bundle's bytes** (a few kB) so it renders correctly on a machine with no build; so does every snapshot sidecar. A recording without provenance is not a regression baseline — and a missing bundle is reported in the HUD, never quietly substituted from the source checkout. **The one permitted hole is declared per port and never global** (`NR-SIM-42`): a `record:` policy of `full` (the default) · `decimate: n` · `excluded`, written in the pipeline beside the wiring, with the policy recorded for **every** declared port so a reader answers *"was this complete?"* from the file alone. An excluded port feeds `R-SIM-23`'s feasible-cut query rather than a second mechanism; excluding or decimating an input a `simulate` stage consumes is a **load error at record time** and merely an infeasible cut at resim time. `sim record`/`sim batch` estimate the size before starting, labelled as an upper bound and revised from the measured rate. |
| R-SIM-7 | **Never re-derive what the SUT already produced — and never estimate what nothing produced.** If a ProPort carries a warning state, draw that state. Where no debug ProPort exists and a layer must reconstruct algorithm-internal geometry from calibration, it is a **marked** stopgap: `derived` style variant, `…(derived)` in the layer panel. The permanent fix is a SIL-only `<fn>.debug` port, which is cheap once R-SIM-4 holds. **"Reconstruct from calibration" is a deterministic transform of a fixed constant or of a value a port/world model already emitted — never integrating a time-varying signal (dead-reckoning, filtering, any history-dependent estimate) into information nobody produced.** That is an algorithm; it belongs in a real component under test, never in a layer provider. |
| R-SIM-8 | **Expectations are data, from one source.** A scenario's acceptance criteria live in its `expect:` block — not in a comment — and the same block drives the timeline marker, the headless `sim check` and the report. Every timing predicate carries an explicit `within_s`; there is no default tolerance. An anchor time that was derived offline records where (`from:`), matching the calibration provenance discipline. |
| R-SIM-9 | **The bundle and `shared_config` hold real runtime configuration only.** A file enters the config bundle **iff some component's DLL reads it at run time**; `shared_config` is real-vehicle/runtime data, never simulation data. World-model bindings (map, spawn index, blueprints), sensor **error** models (noise, latency, dropout, occlusion, `object_range_m`, `num_object_slots`) and fault injection live with the tooling — per-scenario in `world.*` / `run.faults`, reusable in `modules/df/sim/sensor_models/`. Corollary: **real sensor poses/FOV/ranges and class footprints are already runtime calibration** (`BSD_SENSOR_*`, `BSD_CLASS_*`, read by `bsd_params.cpp`) — a sensor model **references** them, never restates them. `BSD_SENSOR_0_RANGE_MAX_CAR_M` (what the ECU believes) and `object_range_m` (what the sim feeds) are different numbers; never merge them. |
| R-SIM-10 | **Per stage, two independent fields: `mode:` (`simulate`/`measured`/`off`) and `impl:` (`dll:`/`stub:`/`stubdll:`).** A stage's interface is its port set, and *executed* and *injected* produce the same port set — a consumer cannot tell which it got. That single invariant is what lets one tool cover every level of simulation, exactly as a measurement/resim console needs to, with its per-component take-from-measurement toggle. Consequences: **any cut, not one cut** (`mode` is per stage, wiring is per port); **depth is data** (ground-truth objects → real perception → RSP in the loop changes `mode`/`impl`, and a downstream component's entry stays **byte-identical**); a stand-in for a not-yet-existing component is a **stage**, never a source feature; `impl:` is **retained on a `measured` stage** so the toggle is reversible; and `mode: measured` against a recording lacking that stage's outputs is a **startup error**, never a partial injection. **A `measured` stage between two `simulate` stages on one data path is a severed chain** — the upstream stage computes into nothing and the downstream stage never sees it, so the toggle lies. Setting a stage to `simulate` therefore **closes the gap by default** (intervening stages flip to `simulate`, undoably); forcing the gap back open is allowed — it is how one stage's divergence is watched while a downstream stage is held on known-good input — but the orphaned stage is then badged *"computed, not consumed"* in the GUI and warned at load headlessly. Never silent, never forbidden. **There is never a second implementation of the same stand-in:** the native host (`modules/sim`'s `simcore`/`simengine`, which superseded `sil_host` — retired 2026-08-23, WP-16) runs `dll:`/`stubdll:` stages plus `mode: measured` injection, and **never grows its own object generator** — if a stand-in must run without Python it is promoted from `stub:` to `stubdll:` on the same generic ABI. A pipeline asking for a level the source cannot emit is a startup error naming both ends. |
| R-SIM-11 | **A host must not require generated protobuf bindings or a sibling checkout.** `adasManifest()` carries the `FileDescriptorSet`, so message classes are built at run time from the DLL that produced the bytes — no `interfaces/build/generated_py`, no proto codegen, no component-specific import in framework code. Combined with `adas-sim` being a Conan package and the config bundle travelling beside the DLL (R-SIM-3a), a component's resim needs **only that component checked out**. Generated bindings may be *used* when present; they must never be *required*. |
| R-SIM-12 | **Producing a recording and executing one are two sides, joined only by the artifact.** A *mock* (a stand-in manufacturing a port's data) belongs on the **production** side by default — freeze its output into the mcap, then resim with that stage `measured`. That makes an algo test a file plus a pipeline, reproducible with no world model present. A live `stub:` stage is for the narrow case where the mock must react to something computed in the loop. **Which cuts a recording supports is a property of the recording**, read from its topic index, never guessed. **Every topic carries an origin tag** — `measured` / `truth` / `mocked` / `simulated` — because a manufactured recording and a real one share a format, not an evidence grade; a report must never let "perception was measured" mean "perception was a mock". CLI verbs name the sides: `sim record` produces and executes nothing, `sim run` does both, `sim resim` executes an existing artifact. |
| R-SIM-13 | **The viewer never talks to a world model, a DLL or a file — it renders a `Session`.** So visualization is identical across every foreign simulator, mcap and real measurements; nothing in the visualization spec may name a world model or a file format. **No live world-model client exists** (`DD-12`) — a foreign simulator (CARLA, CarMaker, …) reaches the system only as a codec plus an ingest map (`SYS-0109`, `R-SIM-23`), never a live integration. Closed loop (our code inside a foreign process) is **parked**: it would be enabled by a `Pipeline` exposing the same generic ABI as a single `SilComponent`, and needs no design until a scenario requires it. |
| R-SIM-14 | **A recording is a model; a format is a codec.** The model is `meta` + `topics{schema, provenance}` + `(topic, log_time_ns, capture_time_ns, bytes)` — **two integer-nanosecond clocks, not one** (`CR-SIM-4`, `OD-9`): `log_time_ns` is **reception** (the scheduling clock — it groups messages into ticks and drives resim, unchanged) and `capture_time_ns` is **validity**, the instant the data describes. `capture_time_ns` is `None` when unknown and is **never defaulted to reception**, because equality would manufacture an `age_s` of exactly `0.0` indistinguishable from a true one; `Capabilities.capture_time` declares support and a codec without it degrades explicitly. `PortValue.age_s` is *derived* from capture when known, else from the hold schedule (`R-SIM-18`). `Session`, pipeline, Scene, viewer and expectations are written against the model and **never against a format** — no layer provider, renderer or expectation may learn a format exists. A new format (rosbag, MDF4/MF4, CarMaker results) is one reader/writer of ~4 methods each, in `adas_sim.io.<fmt>`, registered by extension. **Codecs declare capabilities** (`embedded_schemas`, `random_access`, `meta_blocks`, `arbitrary_topics`) and a missing one degrades explicitly, never silently. Keep `io/` (format codecs) distinct from `sources/` (the scripted stimulus source and its recorder — the live world-model client is removed, `DD-12`) — different abstractions, different reasons to change. **Readers and writers are symmetric** — a format that can be read is registered to be written wherever its capabilities allow, which makes `sim convert` a consequence of the codec table rather than a feature. **A *recording* and an *export* are different artifacts:** a recording round-trips and can be resimmed; an export (CSV, video, plot data) is lossy and terminal, selects an explicit **port subset** by manifest name, flattens to a declared column/field schema, and carries the same `log_time_ns` timebase and origin tags as its source. An export is never accepted as a resim input, and a codec that cannot round-trip is registered **write-only** so the loader refuses it by capability, not by convention. |
| R-SIM-15 | **A port's value is overridable in the pipeline, from a closed verb list.** Four arithmetic verbs — `const` · `hold` · `offset` · `scale` — plus two structural ones, `select` · `drop` (`OD-8`, closes `OQ-10`). Addressable at a port, a field path (`egoDyn.vx`) or a repeated element by a **closed index grammar**: `[i]` and `[*]` only, **never a predicate**. The line that keeps the list closed: **an override may destroy or attenuate information; it may never create an entity** — `R-SIM-7` one level up, which rules out `insert`/`move`/`duplicate` on principle. A port declared `fixed_slots: true` in `conf/ports.yaml` **clears an element in place and never compacts**, because compaction renumbers indices and breaks track association silently. Time-varying and conditional overrides stay refused: the answers are *edit the scenario* (also data) or a `stub:` stage. This is what "tweak the inputs" means to a developer, and having it is what stops a private fork of the host. **The list is closed and stays closed** — no expression language, no scripting hook, no user-supplied callable in a pipeline file. An open-ended per-argument mapping scheme is the failure this bounds: an open expression grammar is how a flexible tool becomes an over-configured one. An override is **declared, never smuggled** — it appears in the run manifest beside the config-bundle hash (`R-SIM-3a`), and an overridden port is badged in the HUD and tagged `origin: overridden` on its topic (`R-SIM-12`). |
| R-SIM-16 | **One engine, two faces — and a component onboards itself.** The interactive developer face and the batch project-scale face are **front-ends over one engine, one pipeline schema and one recording model**; the developer's project file *is* the input to the mass run, with a scenario list wrapped around it. Two engines would mean two namespaces, two project formats and — fatally — the developer validating something other than what the project runs, destroying the audit value that the batch face exists for. Consequences: **the framework is a library first and an application second** (no logic in `cli/`/`app/`; every capability usable in ~3 lines from a script or notebook, which is how a feature gets borrowed under duress); and **a new component is onboarded by building on the generic ABI, never by a handoff** — `sim probe <lib>` reads its port set from `adasManifest` (`R-SIM-4`), so there is no port-mapping step and no ticket to a platform team. Hand-mapping a port set we own would create a second description free to drift from the manifest. **`impl: "legacy:<lib>"` is the sole exception**, for binaries that genuinely cannot carry a manifest (supplier deliveries, prebuilt third-party); the verbose per-argument wiring is quarantined to those stages and is never the default path. |
| R-SIM-17 | **Transport is defined against the head, and stepping backwards never fabricates state.** The **head** is the furthest tick computed. *Behind* the head the Session is immutable data: seek, scrub, step back and re-render are free and never re-execute the SUT (`§6.4`). *At* the head, execution advances: run/pause, step forward, and advance-N (`50`/`100`/`200`/custom) as one uninterruptible job with progress and cancel. **Stepping backwards therefore leaves execution mode and enters review** — it is never an inverse `exec()`, because the SUT holds state the ABI does not expose. Resuming forward from behind the head offers exactly two honest choices, both named in the UI: **skip to head**, or **recompute from tick 0** (deterministic resim only, `R-SIM-5`). Silently continuing from a rewound position, or interpolating a state the DLL never produced, is the fabrication this rule exists to prevent. |
| R-SIM-18 | **Rate is declared, the schedule is derived, and jitter is injected — never simulated.** A stage declares `period_ns` in its manifest beside its ports (`R-SIM-4`), so rate is *discovered* like everything else. The **base grid is the GCD of the declared periods**, derived not configured; a period that is not an integer multiple of it is a **load error naming both numbers** — never rounded, because a rounded period accumulates into drift that reads as an algorithm bug. A stage executes only on its due ticks; otherwise its outputs are **held** (`updated=False`, `age_s` growing from integer nanoseconds), which is exactly what a consumer sees in the vehicle. **The consumer contract is unchanged** — a stage always receives its full port set, so `R-SIM-10`'s invariant survives. **The scheduler is ideal by design:** jitter, latency and drop are sensor/bus *error models* (`R-SIM-9`), injected per scenario and therefore testable. A runner that jitters cannot tell you whether your algorithm is sensitive to jitter. Resolves `OQ-2`. **Where a sample time is *configured* vs. *declared*:** the component owns its rate and states it in its manifest — the host never sets it, because a rate a host could override would let the picture disagree with what the ECU runs. But the number itself is **calibration**, so it is read from the config bundle (`R-SIM-3a`) and merely *reported* through the manifest; a C++ literal would put a real vehicle parameter beyond reach of a calibration sweep (`NR-SIM-6`). **Resolved 2026-07-31 (`OQ-12`, `OD-12`):** the period is read from the config bundle as **integer microseconds** (`<COMPONENT>_<FN>_PERIOD_US`, `R-NAME-3`) — not seconds, because a YAML float re-introduces exactly the rounding drift this rule refuses — and it is declared **per function**, decided now because moving later changes the manifest schema, the scheduler's unit of dueness and every consumer's `updated`/`age_s` reasoning. **No ABI parameter is added:** a component is scheduled at the GCD of its own functions' periods and decides internally what to run (it reads the same bundle and knows its `ENABLED_FUNCTIONS`); the ports carry their function's period so `updated`/`age_s` stay correct per port. **The DLL's own `updated` flag is authoritative over the predicted schedule** — a disagreement is reported, never hidden, because a component whose rate gating has drifted from its declared period otherwise surfaces months later as an unexplained stale value. Short answer to "is sample time in SIL or in sim": **declared by SIL, scheduled by sim, calibrated in the bundle.** |
| R-SIM-19 | **A component under test may crash or hang, and must not take the run with it.** §5.14 classifies errors the framework can *observe*; this covers the process dying. **Isolation is a property of the face, not a global setting:** Bench runs **in-process** (a crash should be immediate, with a stack and a debugger attachable), `sim batch`/Campaign runs **one subprocess per recording** (isolation at run granularity, so per-tick cost is zero), plus an explicit per-stage `mode: isolated` for bisecting which stage crashes. **A per-`exec()` timeout is required, not optional** — a hung library is as damaging as a crashing one and harder to diagnose, because the symptom is "still running". **`fail` / `crash` / `timeout` are three outcomes and are never merged**: they send different people to investigate. Every crash records recording, pipeline, last tick, captured stderr and `run_id` — exactly what `Open on Bench` needs to reproduce it in-process, which is the loop that makes crashes get fixed rather than retried. |
| R-SIM-20 | **A component's plug-ins are authored in the component and *deployed* beside its library.** `modules/<name>/sim/` stays the single authoring home (`R-SIM-1` — moving layers into `modules/sim` would put a function's name in the framework and recreate the defect this design exists to close). But **a checkout is not a delivery mechanism**: the build copies that directory into `<library_dir>/sim/` exactly as it copies the config bundle into `<library_dir>/config/` (`R-SIM-3a`), with the same `bundle.sha256` discipline, and the player discovers plug-ins from a **plug-in path** of library directories. So *"point Vantage at a folder of DLLs and it draws them"* is true by construction: no sibling checkout, no `PYTHONPATH`, no rebuild of the player to add a function (`FR-SIM-70`). A recording embeds the plug-in bundle's **hash and identity, never its bytes** (`NR-SIM-44`) — opening a colleague's file must never run their code, and a missing plug-in degrades to *"these layers unavailable"*, named with the hashes expected. **The asymmetry with the config bundle is deliberate and stated so nobody "fixes" it: configuration is data, a plug-in is code.** The plug-in API carries its **own generation**, independent of the Scene major and the ABI, declared in `modules/<name>/sim/plugin.yaml` — **a file, not a module attribute, because the player must decide before importing**, and importing an incompatible plug-in is what "refused, not half-loaded" forbids; the same file carries the bundle hash, so it replaces a side-car rather than adding one. **Authoring home and deployed form are different questions** — conflating them is what makes "the framework is standalone" and "the picture lives with the component" look like a contradiction when they are not. |
| R-SIM-21 | **A plug-in binds ports through the manifest; a port address is never a literal in a plug-in.** A layer provider, viewpoint, pipeline, workspace or `expect:` block names a port by **manifest lookup on its own component**, never by a spelled string like `"df.bsd.outputs"` — that string encodes a *pipeline-authoring choice* (the stage name) plus a port name, so a stage renamed in a pipeline, or a port renamed in C++, silently unbinds it. **Silent is the whole problem**: an unbound `requires` today returns an empty layer, which on screen is indistinguishable from "the algorithm did not fire". Therefore: a plug-in declares the port it needs **relative to its own component** (`self.bsd.outputs`); resolution to the run's actual address happens once, at load; and a name that resolves against no manifest is an **`AuthoringError` naming the plug-in, the requested port and every port the manifest does declare** (`N-8`) — never an empty tuple. This is `R-SIM-4`'s "named and discovered, never positional" applied to the *consumer* half, which `R-SIM-4` left implicit. **`GT-11`'s `source.<port>` exemption, decided in writing here (`AR-54`, 2026-08-07):** unlike a spelled stage name, `source` is a **reserved keyword in the pipeline grammar** (`contracts/pipeline.py`'s `producer_name == "source"`, checked literally, listed as the alternative to a declared stage name in that module's own error hint) — never an authoring choice a pipeline could rename, so the concern this rule exists to prevent (a stage renamed, a reference silently unbinding) does not apply to it the way it applies to a spelled stage name. `source.<port>` is therefore exempt from the literal-address ban on the same footing as `self.<port>`, but it is **not equivalent** to it: `self.<port>` *resolves* (matched against `known_ports` by the segment after the producer prefix, whichever producer that turns out to be); `source.<port>` does **not** — it is used verbatim, relying on the port genuinely being source-fed in this run. **Trigger fired for real, 2026-08-26 (`E2E-07`), and the naive migration does not work — a real subtlety this row did not anticipate.** `E2E-07`'s scene-parity comparator resim'd `df` as a `mode: simulate` stage (`df_only.yaml`) instead of a `Source`: Python's `objects_layer`/`hud_layer` (`df.common.objects`/`hud`, keyed on `gen_object_list`/`veh_dyn`) silently produced zero layers against the enriched recording, exactly as predicted. But moving both `requires=` entries to `self.objects`/`self.egoDyn` **broke the bare-`Source`-replay case instead** (the phase-1 golden corpus's own consumption path, no `Pipeline` in the loop) — reverted. Root cause: `self.<port>` matches by **port-name suffix**, and that suffix is only producer-invariant *inside a `Pipeline`*, whose `inputs:` mapping (`df_only.yaml`'s `objects: source.gen_object_list`) is what renames a `Source`'s own native topic to the stage's declared port name in the first place. A **bare** replay (`build_session_from_recording` with no `Pipeline`, e.g. this exporter, `modules/sim/tests/fixtures/export_scene_ndjson.py`) never performs that renaming — its `known_ports` carry `Source`'s own native names (`source.gen_object_list`, never `source.objects`), so `self.objects` matches nothing there. `self.bsd.outputs` (this row's own worked example) never hit this because it names an algorithm *output* with no `Source`-native form to begin with — it simply resolves to nothing on a bare replay (the layer gates out, `bsd.warning`'s already-documented raw-corpus absence), never a name collision. `objects`/`egoDyn` are different: they exist under **two genuinely different names** (`Source`'s own vs. the stage's declared one), unified only by a `Pipeline`'s own aliasing — so `self.<port>` cannot serve both the bare-replay and the pipeline-computed case with one reference. **Resolved 2026-08-26, same day, the second option above — a resolver that tries both forms, promoted to a first-class mechanism rather than an ad-hoc per-layer branch.** `LayerCtx.port_any(*refs)` (`modules/sim/src/adas_sim/session/history.py`) tries each of `refs` in order against `known_ports` (`try_resolve_component_ref`, tolerant — no `AuthoringError` until every alternative has failed) and reads the first that resolves; a `layer_provider`'s `requires=` gate accepts a **tuple** of alternatives per signal (`requires=(("self.objects", "source.gen_object_list"), ("self.egoDyn", "source.veh_dyn"))`) and must list them in the identical order `port_any` is called with, so gating and resolution can never disagree about which alternative fired (`modules/sim` commit `09669cb`, "feat(sim): self.\<port\>/source.\<port\> alternation for requires="). `df`'s `objects_layer`/`hud_layer` (`modules/df/sim/layers/common.py`) now use exactly this (`df` commit `a1e4ade`) — the naive `self.<port>`-only migration this row documents as reverted is not what shipped; both names are tried, first-match-wins. **Verified 2026-08-27:** every existing case in `modules/sim/tests/unit/test_b1_df_layers.py` (17/17 passing) exercises `objects_layer`/`hud_layer` against bare-`Source`-native ports (`source.gen_object_list`/`source.veh_dyn`, via that file's own `_make_tick` fixture) — real regression coverage for the bare-replay side of the alternation. The `Pipeline`-aliased `self.<port>` side is not separately covered for `objects`/`egoDyn` specifically in that file, though the same `port_any`/tuple-`requires=` mechanism is shared with other already-working `self.<port>` cases (e.g. `self.bsd.outputs`) — a dedicated `objects`/`egoDyn`-under-a-`Pipeline` test would close that gap fully but was not found to exist as of this note. **Path note, 2026-09-07:** the three Python paths this row cites as evidence — `modules/df/sim/layers/lca.py`, `modules/sim/tests/unit/test_b1_df_layers.py` and `modules/sim/tests/fixtures/export_scene_ndjson.py` — are **no longer present**, retired with the Python providers when `SM-10` moved plug-in authoring to `viz`'s C++ `SceneBuilder` (`D-4`: a Python provider is prototyping-only and never ships). The reasoning above is the reason this row exists and stands; the paths are dead citations, kept because deleting the evidence would leave the rule looking arbitrary. **The C++ `requires:` grammar (`viz` manifest format 4, 2026-10-20):** `x` is required; `a | b | c` is one required group satisfied by any member — alternative names for one port, the C++ form of the Python tuple alternation above; `"?x"` (quoted in YAML) is optional and never badges a layer. A layer is unavailable iff a required entry or group is unsatisfied, and the diagnostic names it with every port the tick carries. Every name resolves through `viz`'s one `ResolveTickPort` (stage-qualified preferred over bare, two stages ambiguous), so binding and `--explain` cannot disagree (`GT-9`). |
| R-SIM-22 | **The per-component generic-ABI shim is generated from declared data, never hand-written.** `R-SIM-4` removed the growth *per function* from the ABI; without this rule the same growth returns *per component*, as ~400 lines of near-identical port table + manifest builder + `adasExec` dispatch that every one of N components hand-writes and hand-maintains. The port set is declared once as data in the component (`conf/ports.yaml`, alongside `conf/build.yml`, `R-VAR-3`), gated by `ENABLED_FUNCTIONS` (`R-VAR-5`); the build generates the table, the manifest builder and the dispatch bindings from it. **The generated shim is a build output, never edited and never checked in** — and the checked-in `<component>.ports.yaml` mirror becomes a *dump of what was compiled*, not a third hand-maintained copy. Consequence: a new component onboards by writing a declaration and linking a generated file, which is what makes `R-SIM-16`'s "a component onboards itself" true in the build rather than only at run time. |

| R-SIM-23 | **A recording declares what ports it provides, through an ingest map owned by whoever owns the recordings.** `R-SIM-6` makes topics equal port names *for recordings this framework produced*. Every other recording — today's legacy exports, another team's test runs, a supplier's or a foreign simulator's output — carries its own topic vocabulary, and the bridge from *"what is in the file"* to *"which port does this satisfy"* is **declared data, not code**: an ingest map under `modules/<name>/sim/ingest/`, authored where those recordings are owned (`R-SIM-1` — a topic named `df/gen_object_list` is `df`'s fact, not the framework's). It states `provides:` (topic → port + `proto_type` + origin tag) and, explicitly, `absent:` (a port this family never recorded, with the reason) — because a known hole declared is a startup answer, while a hole discovered is a run that fails at tick 0. **The map is a closed vocabulary: renaming and tagging only.** No expression, no unit conversion, no field arithmetic, no derived signal — the same boundary `R-SIM-15` draws and for a stronger reason: a preprocessing step that *computes* sits between the recording and the SUT as an unversioned algorithm, so a resim would reproduce the recording plus whatever the preprocessor did, destroying `R-SIM-5`'s determinism and `R-SIM-7`'s "never estimate what nothing produced". A type that does not match the port's declared `proto_type` means **this recording does not support that cut** — never a silent coercion. **Consequence — the answer is computed before the run, not discovered by failing one:** given a recording and the manifests present, the set of feasible cuts is derivable and is reported by `sim probe` and the start page (`CR-SIM-21`, made mechanical). |

| R-SIM-24 | **Determinism is measured along the axes that break it, and tolerance exists only where a difference is legitimate.** `R-SIM-5` makes resim deterministic *by design*; this makes it **evidence**. Reproducibility is reported separately for: same process · fresh process · rebuilt binary · **different machine** — because the failures that actually occur (FP contraction, a different `libm`, unordered-container iteration, uninitialised memory that is stable locally) are invisible to a same-process re-run, which is all today's `ST-C2-2` exercises. **The comparison is over port values, never file bytes** — a recording carries a `run_id` and a timestamp, so two recordings of one deterministic run are never byte-identical files. **The axis is derived from the two runs' manifests, never declared by a flag** (`host`, `process_nonce`, `library_sha256`, `build_id`, `config_bundle_sha256`); a pair differing in more than one dimension is not evidence for the narrower axis and the report says so. **Two gates and two measurements, not four gates** (`OD-10`): same-process and fresh-process must be **exact** and block CI; rebuilt-binary and different-machine are **measured, declared and tracked**, because bit-identity there is not always achievable and mandating it produces a red build nobody can fix and a tolerance that widens to hide it — and a divergence on those two axes is a finding about the **component**, not about the framework. **Tolerance therefore exists only on the last two axes** — the first two have no tolerance *field*, so there is nothing to widen. It is declared per component (`modules/<name>/sim/tolerance.yaml`, beside the ingest map, `R-SIM-1`), `default: exact`, integers and enums exact and not overridable, **every row carrying a mandatory `why:`**, its hash in the run manifest — and **a passing report prints the tolerance it used and the headroom consumed**, which is the only anti-spiral mechanism that does not depend on someone choosing to look. A divergence is reported with the first diverging tick, port, field and the bound in force; a bare pass/fail is not a determinism result. |
| R-SIM-25 | **Every rendered value is traceable to the bytes that produced it.** For any prim, layer or plotted sample the tool answers, in one action: which port · topic · tick · origin tag · config bundle · component build — and whether the value was **published by the SUT or reconstructed by a layer** (`R-SIM-7`). The pieces already exist (`Prim.pick_id`, `PortValue.origin`, per-topic provenance, `bundle_origin`, `run_id`); this rule is that they are **joined**, and that the headless path (`sim explain <signal> --at <tick>`) answers identically to the GUI, or the GUI has become the source of truth. **The join needs no new capture and no new index** (`OD-6`): `run_id` → the manifest, `Layer.id` → the provider's *resolved* `requires` → ports → topics → origin, `pick_id` → the entity. Two rules carry it: **one producer, two formatters** — `evidence(address, session, tick)` returns one record; the GUI panel renders it and `sim explain` prints it, so identical answers are structural rather than a discipline (`GT-9`'s own shape) — and **a field it cannot fill reads `unknown`, never a plausible default** (`NR-SIM-4`, on the one surface whose whole purpose is being believed). `Prim` carries `derived` per prim, because a layer legitimately mixes SUT-published and reconstructed geometry; `Layer.derived` keeps the panel badge and the two are bound so they cannot disagree. `@signal` declares its inputs like `@layer_provider` does, or computed plot samples end the chain invisibly. The chain stops at the component boundary — it says *where a value came from*, never *why the algorithm produced it*. **Why this outranks features:** the way a visualization tool dies is not a crash — it is a developer who cannot confirm what they are looking at, stops believing it, and returns to `printf`, after which every other capability is sunk cost. It is also what makes the strongest available claim true: *every number this tool shows can be traced to the bytes that produced it.* |
| R-SIM-26 | **What the function gets is what viz shows.** Viz draws the inputs exactly as the function received them, held exactly as the sim bus holds them (`PortBus::Get`, no viewer limit), plus the function's published outputs. **Viz adds no intelligence:** no thresholds or limits of its own (the 1.0 s `hold_limit_s` was removed 2026-10-22 for this reason), no delays, smoothing or emphasis, and no history kept between ticks. Staleness is the function's own published verdict (e.g. `INPUT_STALE`). A function's own layer may help a reader perceive *this tick* — calibration geometry and the function's own stateless calls over this tick's values, drawn `derived` (`R-SIM-7`) — but it never re-runs a decision that depends on the function's history, and never draws a raw input beside an output the function computed on a corrected version of it. Anything the function corrects or decides internally that must be plotted is **published by the function** (an output field or a SIL-only `<fn>.debug` freeze port) and drawn from there. |
