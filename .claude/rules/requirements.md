# Rules — Requirements & Verification (R-REQ)

Normative index — **the rule only**. Rationale, procedure and the mistakes each
rule exists to prevent: `skills/requirements_management.md`. Step-by-step:
`workflows/write_requirements.md`. Templates: `templates/requirements/`.

A requirement set is a **V**: requirement layers down the left arm, test layers
up the right, joined only by trace links. **Which layers a module populates is
declared per module** (`R-REQ-12`) — all four is one valid choice, not the only
one — and a row whose obligation has nothing to say at the layer in between
**traces past it, declared and counted**, rather than getting a bridge row that
only restates its parent.

| Layer | Requirement | Tests | Proves |
|---|---|---|---|
| Stakeholder | `STK-nnnn` | `STT-nn` · `E2E-nn` | **Validation** — does it solve the stakeholder's problem |
| System | `SYS-nnnn` | `SYT-<area>-nn` · `INSP-nn` | **Verification** — does the boundary behave as specified |
| Software | `SW-nnnn` | `UT-<item>-nn` · `IT-nn` | Each software item, internally |
| Impl/Design | `IMP-nnnn` → `WP-nn` | build gates | Which file, which symbol, in what order |

`ANL-nn` (analysis) attaches to whichever layer declares it in `layers.yaml` —
system where it checks the assembled boundary, software where it checks source.
`<area>` and `<item>` tokens are declared once in the document's §0 and never
invented at the point of use.

| ID | Rule |
|---|---|
| R-REQ-1 | **One obligation, at exactly one layer.** A statement belonging a layer up is **moved, never copied** — a rule in two places drifts. Children are found by inverting trace links, never by a hand-kept list. |
| R-REQ-2 | **A UID is allocated once, in creation order, never changed and never reused**, independent of the heading number. A retired requirement moves to a disposition section naming its replacement, so a dead link lands on an explanation. The module is the namespace; qualify (`SIM:SYS-0001`) only across modules. |
| R-REQ-3 | **Requirement anatomy is fixed:** `**UID** · priority · release — headline`, then **Shall** (one obligation), **Accept** (the falsifiable observation deciding pass or fail), **Verify** (method + test ids), **Trace** (parent UIDs, or `—` at the top declared layer). An `Accept` that no observation could contradict is a motivation: demote it to prose. |
| R-REQ-4 | **A test never restates an `Accept` clause** — it cites it by UID, because a reworded copy is free to drift. A test contributes only what the requirement cannot know: `Serves`, `Fixture` (from a named catalogue), `Steps`, and its cases. |
| R-REQ-5 | **A test case is the unit that passes or fails**, identified `<test-id>.cN`, with pass criteria written so they can be false **and the FAIL side stated**. One outcome, one case, inline; enumerate only genuinely independent outcomes. **A case that cannot fail is not a case.** |
| R-REQ-6 | **Verification status is derived, never stored in a specification.** No requirement or test document carries a `Status` column. Pass/fail, date, operator and comments live in a **Test Execution Record** — one per campaign, `<MODULE>_Test_Execution_<date>.md`, joined to cases by ID. |
| R-REQ-6a | **Implementation progress is a different question from verification status, and may be carried in a requirement document — generated, never typed.** Permitted only under **both** conditions: exactly one hand-maintained source (the plan's checkboxes, every layer above rolled up from it), and the ordinary check recomputes every mark and fails on disagreement. Three box states: `[x]` done · `[ ]` not started · `[~]` started **and saying `closed by <command or condition>`**. It authorises *work done*, never *requirement met*. **A checkbox row states the work, not the story of doing it** — one line naming what it lands, with the detail in the design rows it points at, because a plan whose rows grow a paragraph each time someone touches them stops being a build order and becomes a diary. **Mechanised 2026-09-05 in `templates/requirements/trace_check.py`, opt-in:** a set declaring `plan:` in `layers.yaml` gets `C-UNLANDED` (a requirement in the lowest declared layer that no work package lands — invisible to every other check, because the requirement itself is well formed and simply has nothing that will build it), `C-DUPLAND`, `C-PLANUID` and `C-PLANMARK` (a `[~]` with no resume condition), plus `--status` derived wholly from the checkboxes. **The hand-maintained source is the *design row*, not the work package** (2026-09-06): a `row_style: table` design layer carries a **leading** `Box` column — first, always, so a reader never counts cells to find the state — and a package's own box is **recomputed from the rows it lands** — all `[x]` → `[x]`, all `[ ]` → `[ ]`, anything between → `[~]` — with `C-WPROLL` failing on disagreement, `C-ROWBOX` on a design row carrying no box and `C-ROWMARK` on a row `[~]` that does not say what closes it. **The same rollup extends to any supporting document that carries its own build order**, declared `rollup: true` beside its `context:` entry (`R-REQ-17`) — a **delivery design** is the case that forced it: the viz layers, the sim fixtures, the CarMaker roads and the CARLA corpus are real work with real packages, and leaving them out of `--status` is how *"the algorithm is done"* comes to be read as *"the function is done"* while nothing can yet draw it or drive it. Ids there are scoped to the document and allocate no UID, so the checker matches them generically (`WP-<anything>`, `<PREFIX>-<digits>`) and stays module-agnostic; `C-ROLLUP-EMPTY` catches a `rollup: true` on a document with no boxed row, because a declared rollup that rolls nothing up reads as coverage. **This is what made the "recomputes every mark" half of this rule true rather than aspirational**: while the package was the finest thing a document carried there was nothing below it to recompute from, so its box was typed and unchecked, and a package half-built was indistinguishable from one untouched — the exact wrong answer `modules/sim/docs/v2` fixed for itself in 2026-08-27 by putting a box on every `IMP` row of its plan. One design row is one buildable artifact (one file, one symbol); a package is a bag of them, so only the row can carry a state that is simply true or false. **The simplest way to satisfy this rule remains not to carry progress marks in requirement documents at all** — then there is nothing to recompute and nothing to drift, and the plan's boxes stand alone. Worked example: `modules/sim/docs/v2/parity`. |
| R-REQ-7 | **The traceability matrix is generated, never hand-maintained.** It is a report that finds defects — orphans, widows, requirements unparented below the top declared layer, dangling links, one-way links and duplicate ids. A copy committed for readability is marked generated and never hand-edited. |
| R-REQ-8 | **Four verification methods, and the weakest that suffices is never the default.** `T` automated execution (preferred always) · `D` demonstration — scripted and evidence-attached, never "we tried it" · `A` analysis — a static check over code or artifacts · `I` inspection against a **named** checklist, so "inspected" can never mean "someone read it". |
| R-REQ-9 | **A test identifier cited by a requirement appears verbatim inside the test that implements it**, so the link is greppable. Corollary: **every `A`-method check ships a planted-violation case** — a check nobody has seen fail is a check nobody should believe. |
| R-REQ-10 | **A threshold nobody supplied is marked `⊘`, never given a plausible number.** Where a test is specified and buildable but its bound is the customer's to set, the row is marked and the open question named. A requirement nobody can fail is a requirement that will be declared satisfied. |
| R-REQ-11 | **A trace link is written from both ends and mechanically checked for agreement.** The requirement names its tests (`Verify`); the test names its requirements (`Serves`). A deliberate second copy — the exception to `R-REQ-1` — because each document must read standalone. **The copy is made safe by checking it, not by deleting it:** the check fails when either half names something the other does not. |
| R-REQ-12 | **A module declares which layers it populates (`layers.yaml`); a trace resolves to the nearest layer declared above.** The **top declared layer is unparented by definition**, never by an exception list. A layer declared but left empty is a finding; one never declared is silence, which is honest. Writing the whole V in one pass and writing one layer mid-stack are equally legal. Adding a layer later is a re-point pass **the check enumerates by name** — never a reason to invent a parent, which looks traced and no check can see. **A layer may also declare that it traces *past* the layer directly above (`may_skip_from:`, added 2026-09-07), and that is not a loophole — it is the same honesty this rule is built on, one level down.** Not every stakeholder obligation has system-level content: *“warn at 2 s”* and *“activate only when A and B both hold”* land inside one software item and state no vehicle-level boundary behaviour, so the `SYS` row written to bridge them can only restate the parent one font-size larger — **one obligation in two places, which is exactly what `R-REQ-1` forbids**, and a bridge row is worse than a gap because it looks like decomposition and no check can tell. The escape is declared, justified and counted: the **layer** declares `may_skip_from: [STK]` (an undeclared skip stays `C-PARENT`, and naming the layer directly above is `C-SKIPDECL`); the **row** says why in its own `Trace` — `` `STK-0007` (skips SYS: one software item, no vehicle-level boundary behaviour of its own)`` — or `C-SKIPWHY` fires; and **every skip taken is printed on every run**, like the budget ratio (`R-REQ-13`), because one skip is a judgement and a set full of them is a `SYS` layer nobody wrote. **Skipping is never the default**: ask first whether the boundary genuinely has nothing to say — behaviour crossing more than one component, a port contract, a timing budget the vehicle owns rather than the software — and skip only when the answer is no. Worked example: `templates/requirements/example` (`SW-0001` → `STK-0005`). |
| R-REQ-13 | **The requirement budget is a declared expectation, reported every run — never a failure.** `layers.yaml` declares a basis (`unit` × `count` × `per_unit`) and a per-layer expectation; the ordinary check **prints the ratio and names any layer over it**, and exits clean. **A ratio, not a fixed number** — a complex module earns a larger set by having more work items. **Changed 2026-09-05 from a hard cap, because the hard cap did the damage it was meant to prevent:** writing `modules/sim/docs/v2/parity`'s `STK` layer against a cap of 10 forced four of its ten rows to carry two obligations each, and the merge was invisible in the finished document — the reader cannot see what was compressed to fit. A count over expectation is a **scope** signal for a human to judge, never something a checker should resolve by silently shrinking the writing. Raising the basis still costs one dated `budget_history:` entry, and that history is **printed on every run**, because a reason kept only in a comment is a reason nobody reads. |
| R-REQ-14 | **Cap the commentary, never the count and never the length.** There is **no cap on how many requirements a set may hold and none on how long a document may be** — a document is as long as the problem needs, and capping either one punishes thoroughness and invites the compression `R-REQ-13` now exists to prevent. Two caps remain and neither is about size: `Shall`+`Accept` ≤ `requirement_words` (60) and headline ≤ `headline_chars` (90) are **one-obligation detectors** — a row over them is carrying more than one obligation (`R-REQ-1`) and is fixed by **splitting the row**, which makes the set better, so they are never raised. What *is* capped is **commentary: every line of a requirement document that is not a requirement field, a headline, a heading, or blank — at `commentary_lines_per_requirement` (6)**. **Measured across every set in this repo, 2026-09-05:** readable documents run **1.6 to 4.3** commentary lines per requirement (`sim` v2's System and Software sets at 2.4 and 1.6, `ldw`'s three at 1.6–4.3); the two that became unreadable run **81 and 990** (`SIM_Implementation_Design`, `SIM_Concept_Document`). Length separated none of them — `sim` v2's System document is 2,689 lines and perfectly healthy by this measure. Commentary separates them by more than an order of magnitude. **6, not 4:** four would fail `ldw`'s own stakeholder document, whose preamble earns its place. **The cap does not apply to an implementation design or plan, nor to a supporting document declared under `context:` (`R-REQ-17`), and that is deliberate.** An `IMP` row's job is to name *which file, which symbol, in what order*, so a design document is expected to be long and dense — `SIM_Implementation_Design_v0.1.md` carries 379 rows, each with a concrete path, and is right to. **A path there is a promise: the code goes at that path under that name.** What is capped in those documents instead is **execution narration** — what was run, what was found, what was fixed, how long it took. That belongs in a Test Execution Record, a commit message or `git log`, never in the plan, and the reason is measured: `SIM_Implementation_Plan_v0.1.md` reached 85 essay-length checkbox rows and had to be compressed by 53% to be readable again. **The test is tense.** A design row says what *will* be true of the code (present or future, a promise a reviewer can hold the diff against); narration says what *happened* during a session (past, an event). A row in the past tense is in the wrong document. |
| R-REQ-15 | **A boundary requirement names the declared port it is observable at; an internal one names the declared software item it constrains.** Names resolve against the component's real `conf/ports.yaml` and the module's declared item list; a name matching neither is a finding. A requirement binding to nothing is scope creep. A set written ahead of the code declares its ports under `ports.proposed:`, reported `PROPOSED`, failing the day the real file disagrees. |
| R-REQ-16 | **The top layer is Stakeholder Requirements, split into declared categories.** `STK-nnnn` is the master set — what the stakeholder asked for — and `layers.yaml` declares which categories it carries: `feature` (*what must it do*) and `kpi` (*how well, measurably*). **A module declares only the categories it has**: an algorithm feature carries both; a cyber-security or embedded item with no performance target of its own declares `[feature]` alone and **is never asked for a KPI it does not have**. The reverse holds too — a declared category left empty is a finding, so the escape is honest rather than silent. **A `kpi` row's `Accept` states a number or `⊘`** (`R-REQ-10`), because a performance target with no figure cannot be measured and will be declared met. |
| R-REQ-17 | **The thinking is a declared document, not a scattered one — and it never carries an obligation.** A requirement set is the *result*; the reasoning that produced it (the domain, the mathematics, the ports, the alternatives rejected) belongs in a **supporting document declared under `context:` in `layers.yaml`**, from a closed list of four kinds: `concept` (why the numbers are what they are) · `architecture` (how it is built) · `register` (the change register — plain English, before any UID exists) · `reference` (retrieved external material; may name a directory). **Three properties make it safe.** It **allocates no UIDs and defines no requirement rows** — *citing* `SYS-0004` is how it connects to the set, *defining* it puts one obligation in two places (`R-REQ-1`, checked as `C-CONTEXT-UID`, which looks for the requirement anatomy and never for a mention). It is **exempt from `commentary_lines_per_requirement`**, because commentary is the entire point of it — what is capped instead is the same thing capped in a design, **execution narration, and the test is tense** (`R-REQ-14`): a document that says what *is* true of the problem is a concept, one that says what *happened* last Tuesday is a diary. And it must be **cited by some requirement document, the test spec or the plan** (`C-CONTEXT-UNREF`) — a supporting document nothing refers to goes on looking true long after the set stopped agreeing with it, which is exactly why `modules/sim/docs/v1/sim_api_reference.md` had to be retired rather than trusted. **Why declare it at all, rather than just writing the file:** an undeclared analysis document is indistinguishable from a stale one, so a reader cannot tell what to read first and a checker cannot tell when it rots. **A context entry may declare `rollup: true`** when the document carries its own build order — a package list plus a boxed design-row table, ids scoped to itself. That is `R-REQ-6a`'s three checks applied to it and its inclusion in `--status`; it allocates no UID and `C-CONTEXT-UID` still holds, because a *build order* is not an obligation. Worked example: the four delivery designs in `modules/df/docs/ldw/` (viz, sim, CarMaker, CARLA). **The block is optional and omitting it is honest** — a set whose reasoning fits in its own preambles needs none. Worked example, all four checks planted and caught: `templates/requirements/example`. |

**Reference implementation: `modules/df/docs/ldw/`** — a complete **four-layer**
set (stakeholder → system → software → implementation design; both `STK`
categories populated, the build order derived from the design rows, and five
build orders under one row-level progress rollup) with a module-agnostic checker
at `.claude/templates/requirements/trace_check.py` (run with `--set modules/df/docs/ldw`; the set holds no copy of it)
driven entirely by `layers.yaml`. **Its counts are
computed, never quoted** — `python .claude/templates/requirements/trace_check.py --set modules/df/docs/ldw --stats` prints them, and a
size retyped into prose is one more thing to drift. **Rebuilt 2026-09-05** from a three-layer,
29-requirement set — its `budget_history` records why each layer grew, and the
superseded set was deleted once this one was signed off (2026-09-05). It is also the worked
example of `R-REQ-17`: the concept and architecture documents that produced it
are declared under `context:` and carry no requirement rows of their own. `--selftest` plants a violation per check and
proves each is caught (`R-REQ-9` turned on the tooling itself).

`modules/sim/docs/v2/` is the reference for **`R-REQ-6a` progress rollup only**
(`--status` / `--write-status` — a module-specific checker, not the template
one). It is otherwise the worked example of `R-REQ-1..11` at the scale
`R-REQ-13`/`R-REQ-14` exist to make *visible* rather than to forbid: read it
for the shape of the fields. Its requirement documents are **not** what those
two rules were aimed at — they measure healthy (`R-REQ-14`) — but its Concept
and Implementation Design documents are, at 990 and 81 commentary lines per
requirement.
