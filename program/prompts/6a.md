## Goal
`modules/vantage/docs/VANTAGE_Architecture.md` exists. Read alone, it says what
each part of Vantage is for and what it never does, how the six rules are kept,
how work is split over threads without changing a result, how failures are
contained, and the file and symbol of every part, so the Plan C requirements
(step 8) and the register (6b) can be written against it.

## Stated inputs (decided; build on them, do not reopen them)
1. **Owner decision (2026-08-27): C++ wherever there is scope; the Python run
   path is legacy.** Say which parts are C++ and what, if anything, stays Python
   and why.
2. **D13:** viz is out of this design; the live measurement is Vantage's output
   boundary. No viewer code, no viz dependency.
3. **D10 and the rule override:** the scheduler is event-driven; no base grid.
   A declared period survives only as the clock of a source with no recording
   behind it.
4. **Writer crash outcome (owner, from the RCT review):** `MeasStatus.outcome`
   has the value crash, but a writer that crashed cannot write it. This document
   decides which process holds the live measurement writer and the components,
   and who writes crash and timeout (R-SIM-19: in-process for the developer face,
   one subprocess per recording for batch, per-stage isolation for bisecting).
5. **RCT rows `IMP-0032`..`IMP-0039`** name a job in `vantage` (control writing,
   input selection, writer `open`/`step`/bulk/oversize, inspector attach/read).
   This document gives each one a file path and symbol, in one table, so those
   rows can later be re-pointed (a design-row edit, D14). Do not edit the RCT
   design yourself.
6. **D16 (owner, 2026-10-30):** a component's `cycle_counter` keeps counting
   through RESTART. Wherever Vantage compares outputs (resim against the
   recording, single- vs. multi-threaded for gate G3, RESTART vs. fresh process)
   it compares *equal outputs* as the RCT SYS preamble defines them — byte-identical
   except each header's `cycle_counter`. Use that term; do not define a second one.

## What the document must contain
Write in simple English: short sentences, one fact in one place, no
narration of what happened (the test is tense, R-REQ-14). It is a supporting
document: no UID of its own, no requirement row (no Shall/Accept), cite RCT
rows as `RCT:SYS-nnnn` / `RCT:IMP-nnnn`.

1. **In plain words** — what Vantage does, its inputs (recording, component
   libraries, run setup) and its one output (the live measurement); one diagram.
2. **Every name, its purpose and its scope** — one table, including every part
   below and every run-setup field. Each name has one meaning and one writer.
3. **The parts** — launcher, orchestrator, runner, per-port sample buffers,
   live measurement writer, live measurement inspector, and the engines (resim
   on a recording now; other engines later through the same writer). For each:
   what it does, what it never does, what it reads and writes.
4. **The run setup** — what it holds (stages, `mode`/`impl`, wiring, each
   stage's trigger input or clock, previous-cycle inputs, the readiness limit,
   overrides, record policy), who writes it, how it maps onto
   `MeasDescription`'s `MeasStage` fields. Thresholds nobody supplied are `⊘`
   (the readiness limit is RCT `Q3`).
5. **The six rules** — for each: the rule, why it exists, what goes wrong
   without it, and where it is enforced (load time or run time) and by which part.
6. **Input selection** — by refSync, the fallback rule, and which `MeasBadge`
   kind each outcome raises.
7. **The engine step** — what one step is (and what "tick" now means), and the
   list of existing features that index by tick and must take the step instead.
8. **Threads** — what may run side by side, why the result is identical
   single- and multi-threaded (gate G3), and what is never shared between threads.
9. **Failures** — fail / crash / timeout, the process model of stated input 4,
   and who writes each `MeasStatus.outcome` value.
10. **The live measurement writer and the inspector** — the writer's three C
    calls (open, step, close) common to every engine; which package ships them
    and why; what the inspector does (attach, dump, check) and how it serves gate G4.
11. **Code layout** — one table: part → file(s) → main symbols in `modules/vantage`
    (existing files named where a part starts from one; new files named where
    not), including the `IMP-0032`..`IMP-0039` mapping of stated input 5. One
    package, `adas-vantage` (D2).
12. **What the lab must give Vantage** — only the interface (recordings with
    controls, refSyncs and the known right answer); the lab's own design is step 7.
13. **Rules this design changes** — each 1v `.claude` rule (or rule part) that
    is superseded or amended here, so the migration back-port is a list, not a search.
14. **Open questions** (each with a recommendation), **Rejected options**
    (each with the reason), **Parked** (each with why it waits).
